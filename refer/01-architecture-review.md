# 架构 Review 总结

> 日期：2026-04-20  
> 基于 `reference/architecture-decision.md` 与 `reference/business-overview.md`

---

## ✅ 架构整体评价

整体设计以中型企业架构标准出发，技术选型主流、扩展性强，适合当前阶段快速落地后持续演进：

- **Next.js + NestJS 分层**合理：BFF 模式屏蔽后端细节，后期扩展小程序 / App 成本低
- **Payload CMS 同进程方案**务实：节省一个容器，管理后台开箱即用，资讯 / 内容运营无需改代码
- **BullMQ 异步队列**适配基础制图场景：自助任务异步处理，与人工个性化制图流程互不干扰
- **Multi-repo 职责分离**：前后端独立部署与版本控制，适合小团队并行开发
- **订单模块统一**：基础制图、个性化制图、论文业务共用一套 `orders` + `payments` 链路，无重复开发

## ✅ 已解决关键问题

### 支付方案（已确认）

注册**个体工商户**后直接接入微信支付 APIv3 + 支付宝开放平台，直连官方 API，无平台风险，费率最优。  
无需第三方聚合支付，原支付模块方案不变。

## ⚠️ 当前风险 & 待处理事项

### 🟡 P1：ICP 备案必须在支付 Webhook 上线前完成

- `notify_url` 要求备案域名 + 有效 HTTPS
- ICP 备案周期：7–20 个工作日（部分省份更长）
- **建议第一周就提交备案申请**，个体工商户营业执照办下来后同步申请支付商户号

### 🟡 P1：数据库选型需在上线前确认（自建 vs 云托管）

初期 `docker-compose` 中自建 PostgreSQL / Redis 可行，但：
- 推荐初期直接用云托管（腾讯云 TDSQL-C / 阿里云 PolarDB 最小规格），自动备份，省运维精力
- 若选自建，必须配置定期备份策略（`pg_dump` + OSS 定时上传）

### 🟡 P2：业务定价尚未确定，影响订单模型与下单页开发

`business-overview.md` 中多个关键项仍为"待决策"：
- 各档会员价格、单次制图定价、个性化制图分档定价、退款策略

建议在开发 `/user/orders` 和支付模块前先拍板，否则订单模型会反复改。

### 🟢 P3：图表库三库同时引入，初期包体较重

ECharts + Plotly + D3 全量引入，首次加载 JS 体积较大。  
使用 `dynamic import` + `ssr: false` 按需加载（已在文档中要求，执行时注意落实）。

## 推荐开发顺序

```
第 1 周（并行）
  ├── 提交 ICP 备案申请
  ├── 办理个体工商户营业执照
  └── 拍板定价决策（见 business-overview.md 待决策项）

第 2–3 周
  ├── 搭建基础设施（云服务器、数据库、OSS、Redis）→ 见 02-prerequisites.md
  └── 本地开发环境初始化 → 见 03-dev-environment.md

第 4–6 周
  ├── bio-web：首页、团队页、资讯页、制图展示页（静态 / CMS 驱动）→ 见 04-bio-web-init.md
  └── bio-api：用户注册 / 登录（手机号 + 微信 OAuth）、会员模块 → 见 05-bio-api-init.md

第 7–8 周
  ├── 支付集成（微信支付 APIv3 + 支付宝，申请营业执照后同步推进）
  ├── 订单模块（基础制图 / 个性化制图 / 论文业务共用）
  └── 基础制图工具页 + BullMQ 任务队列

第 9 周
  ├── 个性化制图页 & 后台创建订单流程
  ├── 作品交付模块（OSS 签名 URL + 通知）
  └── 论文业务页

第 10 周
  ├── CMS 内容录入（首页 Banner、团队资料、资讯文章）
  └── 部署上线 → 见 06-deployment.md
```
