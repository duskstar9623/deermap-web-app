# Deermap Web App 样式治理与开发管理计划（Draft）

更新时间：2026-06-22

## 1. 目标与范围

本计划用于统一项目样式开发方式，降低页面样式重复、主题漂移和维护成本。

当前确认的治理决策：

- 暗色模式：先做技术预留，不做全量页面改造
- 设计令牌：以 CSS Variables 作为唯一来源
- 图表页面：按与普通页面一致的样式治理标准推进
- 样式文件策略：Tailwind 为主，配合少量全局 CSS 与组件级 CSS Modules

## 2. 当前样式管理方式（现状）

- 样式入口：`src/main.tsx` 引入 `src/index.css`
- 样式引擎：Tailwind CSS + PostCSS
- 主题映射：`tailwind.config.js` 将语义色映射到 CSS 变量
- 运行时主题色：存在 `src/constants/theme.ts`（需逐步收敛到变量语义）
- 页面样式：大量 Tailwind class，部分页面存在内联 style 与硬编码颜色

## 3. 样式分层规范（后续统一）

### 3.1 Global 层（全局）

存放位置：`src/index.css`

只允许放：

- reset / base
- 设计令牌（颜色、圆角、阴影、间距、层级、过渡等）
- 少量全局 utilities（必须是跨页面复用且难以由 Tailwind 表达）

不允许放：

- 页面专属样式
- 单组件私有样式

### 3.2 Component 层（组件）

存放位置：组件目录内的 CSS Modules（如 `*.module.css`）

适用场景：

- 结构型样式（复杂布局、伪元素、复杂 hover/状态）
- 组件内部可复用样式片段

建议原则：

- Tailwind 负责原子与布局表达
- CSS Modules 负责复杂结构与状态
- 组件对外只暴露语义化样式接口，不暴露具体色值

### 3.3 Page 层（页面）

存放位置：`src/pages/**`

规则：

- 页面只做数据编排与组件组合
- 禁止新增硬编码颜色与阴影值
- 优先复用 shared/layout 组件，减少重复 class 模式

### 3.4 Token 层（设计令牌）

单一来源：CSS Variables

规则：

- 颜色、圆角、阴影、间距语义统一在 `src/index.css`
- JS 场景（图表、SVG 等）通过语义映射层读取，不定义第二套主色系统
- Tailwind config 仅消费语义变量，不维护业务硬编码色

## 4. “是否需要实际 CSS 文件”的结论

需要，但控制在合理范围。

推荐方案：

- 保留并强化全局 CSS（令牌 + base + 少量全局 utility）
- 新增组件级 CSS Modules，承载复杂结构样式
- 日常样式开发仍以 Tailwind 为主

不建议两种极端：

- 完全零 CSS 文件（复杂状态可维护性差）
- 回到大面积传统页面 CSS（易失控、难复用）

## 5. 分阶段实施路线

### Phase 1：规范落地与基线建立（1 周）

目标：先把规则定住，避免继续新增样式债务。

动作：

- 在文档中固化样式分层与令牌规则
- 建立“禁止硬编码色值”的代码评审检查项
- 选定首批治理页面：home / services / pricing

验收：

- 团队对分层规则达成一致
- 新 PR 不再新增明显硬编码颜色

### Phase 2：令牌统一与组件收敛（1~2 周）

目标：清理双源主题，减少重复样式。

动作：

- 将主题语义集中到 `src/index.css`
- 收敛 `src/constants/theme.ts` 到语义映射用途
- 抽离高重复块（section/card/button）到 shared 或 layout
- 在通用组件中引入 CSS Modules（仅用于复杂结构）

验收：

- 首批页面颜色、阴影、圆角来源统一
- 页面重复样式片段显著减少

### Phase 3：图表页面标准化治理（1~2 周）

目标：将 visualization 页面纳入统一规范。

动作：

- 拆分图表页面的样式参数层、组件层、页面编排层
- 仅保留运行时必须的内联动态样式
- 统一图表页组件的语义样式接口

验收：

- 图表页样式可读性与复用性提升
- 新增图表功能不再复制粘贴大段样式

### Phase 4：暗色模式技术预留完善（并行进行）

目标：确保未来 dark 扩展不被阻塞。

动作：

- 保持 dark 变量结构完整
- 优先保证 layout/shared 组件可被 dark 变量驱动
- 暂不做全页面视觉验收

验收：

- 核心组件不依赖固定浅色值
- 后续 dark 全量改造具备清晰入口

## 6. 开发与评审规则（建议写入团队约定）

每次样式改动应满足：

1. 是否优先使用现有语义 token
2. 是否优先复用 shared/layout 组件
3. 是否避免硬编码颜色和阴影
4. 是否仅在必要时使用 CSS Modules
5. 是否没有把页面逻辑与样式实现强耦合

PR 描述建议包含：

- 本次改动涉及的样式层（global/component/page/token）
- 是否新增 token，原因是什么
- 是否影响暗色预留能力

## 7. 验证与度量

技术验证：

- `npm run lint`
- `npm run build`

人工验收：

- 抽检首页、服务页、定价页、图表页视觉一致性
- 检查是否仍存在新增硬编码色值
- 检查共享组件复用率是否提升

建议跟踪指标：

- 页面内硬编码颜色数量
- 重复样式片段数量
- shared/layout 组件复用覆盖率

## 8. 风险与控制

主要风险：

- 旧页面改造过程可能引发样式回归
- 图表页改造范围大，容易影响功能节奏
- 双语文案变化可能导致布局抖动

控制策略：

- 分批治理，优先高复用页面
- 每阶段结束后做页面截图对比
- 不在同一 PR 同时做大规模样式与业务逻辑重构
